# RimMT V0.4.15 Playtest — Parallel Region/Reachability Decomposition

Primary objective: reduce visible stutter by making existing worker capacity actually fan out across CPU cores before increasing the worker-count cap.

## Scheduler fan-out fix

Earlier `ParallelFor` calls queued many batches but used one `AutoResetEvent.Set()`. One short-running worker could drain the entire burst before peers woke from their polling timeout. V0.4.15 uses semaphore work credits so one queued batch can wake one sleeping worker. The runtime report exposes wake credits, multi-wake calls, parallel batches and timeout-poll recovery. The worker self-test is now a direct proof target: `peakActive` should rise above 1 on multicore hardware.

## Parallel permissive connectivity hint

A map-level connectivity snapshot is built as independent horizontal stripes on normal-priority RimMT workers, then merged off-thread. The snapshot uses a deliberately permissive normal PathGrid graph. It does not call `Region.Allows`, `Reachability.CanReach`, validators, reservations or Job creation off-thread.

Different static components are therefore only used as a proof that a candidate cannot be reached through the captured passable topology. Candidates that remain in the same permissive component still go through live Vanilla `CanReach` and the original validator on the main thread. Destroy-through traversal modes fail closed to Vanilla.

The snapshot is generation-bound. Any PathGrid topology generation change before publication discards the build. The main thread never waits for stripe or merge work.

## Playtest proof targets

- Worker self-test `peakActive` > 1; ideally several workers participate.
- `parallel.regionHint` stripe tasks/published snapshots > 0 and workerFailures = 0.
- No new scheduler failures/rejections or main-thread wait path.
- JobGiver / GenClosest P95 and Max should not regress; visible smoothness remains the first acceptance criterion.
- If all 8 workers become meaningfully saturated before the main thread is smooth, only then consider raising the current worker-count cap for higher-core-count CPUs.
