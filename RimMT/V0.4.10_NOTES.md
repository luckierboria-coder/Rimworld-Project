# RimMT V0.4.10 playtest notes

V0.4.8 bounded captures repeatedly showed the same JobGiver hot chain:

`JobGiver_Work -> GenClosest.ClosestThingReachable -> GenClosest.ClosestThing_Global -> Reachability.CanReach -> RegionTraverser.BreadthFirstTraverse`

The latest 33-package capture observed 55,327 `Reachability.CanReach` calls and 1,510 `RegionTraverser.BreadthFirstTraverse` calls, with 9 packages >=64ms and the slowest package at ~220ms.

V0.4.10 therefore drops the V0.4.9 next-call ordering cache approach and starts again from the V0.4.8 baseline. Its new `parallel.jobPartition` path operates on the current supported custom-global `ClosestThingReachable` call:

- materialize the exact candidate identities once on the main thread;
- snapshot integer positions on the main thread;
- preserve every candidate;
- stable-partition candidates into 16-cell nearest-first spatial rings;
- optionally let an idle RimMT worker calculate only primitive integer ring keys for very large snapshots;
- pass the reordered candidates back into the original Vanilla `GenClosest` call;
- keep `Reachability.CanReach`, WorkGiver validators, reservations, priorities and final Job/result selection on the main thread;
- bypass exact `ListerHaulables` calls so V0.4.6/V0.4.7 and PUAH-owned hauling semantics do not overlap;
- fail closed to unchanged Vanilla order on unsupported or invalid states.

Primary validation metrics:

- `Single-call work partition V0.4.10: reordered`
- `candidatesReordered`
- `workerImmediate / workerWaits`
- JobGiver `avg/p95/max`
- 32-package `slowPackages>=64ms`
- `Reachability.CanReach` calls
- `RegionTraverser.BreadthFirstTraverse` calls

Target environment: PUAH Hotfix V5.2.1 + RimMT V0.4.10 + Butter++.
